# 리뷰 결과

## 요약
- 미커밋 변경사항(스테이징된 테스트 삭제 포함)을 검토했으며, 로컬 표지 Import의 완료 후 재시도를 막는 문제 1건을 확인했다. `flutter analyze`는 통과했다. 테스트와 앱 실행은 하지 않았다.

## 문제점
- [P1] 기존 활성 책의 서버 표지에 다시 첨부하여 재시도가 실패한다.
  - 위치: `lib/features/server_storage_migration/services/server_storage_migration_service.dart:225–231`
  - 새 코드는 로컬 스냅샷의 `pendingBookCovers`에 들어 있으면 서버 ID 매핑 존재 여부만 확인하고 무조건 `uploadBookCover`를 호출한다. 로컬 DB 원본 표지가 파일 경로라는 사실만으로는 서버에도 아직 표지가 없다고 판단할 수 없다.
  - 발생 경로: 로컬 커스텀 책과 표지를 업로드 → 서버 `/complete` 성공 → 완료 응답 유실 또는 `applyResults` 실패 → 로컬 DB에는 원래 파일 경로와 `clientRequestId`가 남음 → 사용자가 재시도한다. 앱 종료가 완료와 로컬 반영 사이에 발생해도 같은 상태다.
  - 새 세션에서 같은 `clientRequestId`의 활성 책을 재사용하면 서버는 기존 HTTP(S) 표지를 유지한다. 클라이언트는 이를 확인하지 않고 표지를 다시 첨부하므로 `/attachments`가 400을 반환하고 새 세션 전체가 정리된다. 로컬 상태는 그대로여서 다시 시도해도 전환이 완료되지 않는다. 노트나 독후감이 없는 책 하나만으로도 발생할 수 있다.
  - 근거: [items 문서](../../../../api-doc/api-me-records-import-importId-items-post.md)의 「커스텀 책 표지 처리」는 `clientRequestId`로 활성 책을 재사용할 때 기존 표지를 유지한다고 명시한다. [attachments 문서](../../../../api-doc/api-me-records-import-importId-attachments-post.md)의 `USER_BOOK` 정책은 기존 HTTP(S) 표지에 대한 첨부를 400으로 거부한다. 이는 문서와 코드 흐름을 대조한 판단이며 실제 서버 호출로 재현하지는 않았다.
  - 추가된 서비스 테스트는 가짜 서버가 모든 표지 첨부를 성공시키므로 이 분기를 검증하지 못한다.

## 개선 제안
- 완료 후 로컬 반영 전 실패로 같은 파일을 다시 첨부하는 문제 → 완료 여부가 불확실한 세션과 업로드 결과를 복구 가능한 형태로 보존하고, 서버 완료가 확인되면 기존 결과를 로컬에 반영하는 경로를 마련한다. 새 세션에서 활성 책을 재사용해야 하는 경우에는 서버 표지 상태를 확인하여 기존 URL을 로컬에 연결하고 중복 첨부를 생략한다. `created=false`만으로 첨부를 생략하면 soft delete에서 복원된 책의 placeholder가 남으므로 활성 재사용과 복원을 구분해야 한다.
- 검증 시에는 표지가 있는 책 하나로 `/complete` 성공 후 응답 유실 및 로컬 반영 실패를 각각 만들고, 재시도 후 서버 저장 모드와 로컬 표지 URL 연결까지 복구되는지 확인한다. 복원된 책의 표지는 여전히 업로드되는지도 함께 확인한다.
