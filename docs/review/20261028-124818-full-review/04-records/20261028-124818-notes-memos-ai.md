# 리뷰 결과

## 요약
메모의 로컬 우선 CRUD와 이미지 한도 검사는 갖춰져 있습니다. 신규 노트 화면의 동기화 후 식별자 유지에 P2 1건이 있습니다.

## 확인 범위
노트 생성·제목 자동 저장, 텍스트/발췌/생각/사진 메모 작성·수정·삭제, 중요 표시, 이미지 교체·다운로드, AI 메모 생성, AI 독후감 초안 진입을 확인했습니다.

## 문제점

### [NOTE-01][P2] 신규 노트 화면이 동기화로 다시 build되면 이미 만든 노트 ID를 잃음

- 근거: [lib/features/book_note/providers/book_note_providers.dart:153](/Users/hagulu/develop/service/BBBook/project/app/bbbook/lib/features/book_note/providers/book_note_providers.dart:153)은 동기화 버전을 구독하면서 매번 `_noteId = args.noteId`로 초기화합니다. 새 노트 화면의 args.noteId는 계속 null입니다. 한편 [lib/features/book_note/providers/book_note_providers.dart:206](/Users/hagulu/develop/service/BBBook/project/app/bbbook/lib/features/book_note/providers/book_note_providers.dart:206)은 생성한 ID를 `_noteId`에만 보관합니다.
- 일반 재현: ‘노트 추가’로 들어가 메모를 하나 저장하고 그 화면에 머뭅니다. 백그라운드 동기화가 서버의 노트 변경을 받아 버전을 올리거나 다른 노트 변경이 반영되면 build가 다시 실행됩니다.
- 영향: 새 노트 화면이 빈 상세로 바뀌고 다음 저장이 다른 새 노트를 만듭니다. 사용자는 한 노트에 계속 작성했다고 생각하지만 메모가 여러 노트로 나뉠 수 있습니다. 이미 저장된 DB 행이 즉시 삭제된다는 뜻은 아닙니다.

## 개선 제안

같은 소유자·책·신규 작성 세션 내 재조회에서는 생성된 `_noteId`를 유지하고 그 ID로 다시 조회합니다. 소유자나 작성 세션이 바뀐 경우와 구분해야 하며, 모든 provider 재빌드를 막는 방식은 다른 기기 변경 반영을 깨뜨리므로 피합니다.

## 확인된 보호 장치

- 제목과 메모 push는 노트별 큐를 공유하고, 요청 중 새 편집이 있으면 dirty를 유지합니다.
- 사진 개수는 화면 스냅샷 외에 쓰기 트랜잭션에서 다시 검사합니다. 기존 사진 교체·유지는 새 사진 추가와 구분합니다.
- 신규 PHOTO는 사진+메모 생성 API를 사용하고, 기존 사진 교체는 업로드와 PATCH를 나눕니다. 로컬 사본은 업로드 후에도 유지합니다.
- 텍스트 중요 표시는 강조 마크업에서 파생합니다. OCR 인식 실패는 사용자에게 알리고 recognizer를 finally에서 닫습니다.
- AI 메모 생성 중 화면 종료를 막고 실패하면 입력을 보존합니다. AI 독후감 API는 저장 전 초안으로 취급합니다.

## 후속 확인 시나리오

신규 노트 작성 중 주기 동기화, 제목 입력 중 앱 복귀, 사진 3장 상태의 교체/추가, 사진 업로드 중 같은 메모 재편집·삭제, 마지막 메모 삭제를 확인합니다. AI 메모 API의 응답 유실 후 재시도는 서버 저장 여부가 불명확할 수 있으므로 중복 여부도 확인할 필요가 있습니다. 이번에는 새 서버 멱등 API 설계를 결함 수정으로 요구하지 않았습니다.
