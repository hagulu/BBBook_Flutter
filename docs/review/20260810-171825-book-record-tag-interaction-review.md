# 리뷰 결과

## 요약

- 태그 삭제의 낙관적 갱신과 변이 동시성 차단은 적절하지만, 태그 추천을 펼치는 시점·크기와 진행 쪽수 입력의 터치 영역에 런타임 문제가 남아 있다.
- 검증: `flutter analyze`는 `No issues found`로 통과했다. 프로젝트 지침에 따라 앱 실행과 테스트는 수행하지 않았다.

## 문제점

- [문제][중간][스크롤/상태] `lib/features/book_record/screens/widgets/tag_section.dart:56`~`:66`은 포커스 후 고정된 250ms가 지나면 섹션 전체(`_sectionKey`)의 하단을 화면에 맞춘다. 추천 데이터는 별도 비동기 요청(`:177`~`:214`)이므로 응답이 250ms보다 늦으면 목록이 삽입되기 전에 스크롤이 끝나 이후 나타난 항목이 키보드에 가려질 수 있다. 반대로 응답이 빠르고 목록이 길면 동적으로 커진 섹션의 맨 아래를 맞추면서 현재 포커스된 입력창을 화면 위로 밀어낼 수 있다. 상위 화면도 `lib/features/book_record/screens/book_record_screen.dart:117`~`:118`의 단일 스크롤이어서 이 타이밍 경합을 보정할 별도 목록 스크롤이 없다.
- [문제][중간][성능/레이아웃] `lib/features/book_record/screens/widgets/tag_section.dart:124`~`:127`은 빈 검색어에서도 추천을 노출하고, `:185`~`:211`은 API가 반환한 전체 태그를 제한 없이 `Wrap`의 자식으로 만든다. 기존의 `take(8)` 제한이 제거되어 누적 태그가 많은 사용자는 포커스 한 번에 모든 칩을 빌드·레이아웃해야 하며, 섹션 높이와 스크롤 이동량도 태그 수에 비례해 커진다.
- [문제][낮음][데이터 요청] `lib/features/book_record/screens/widgets/tag_section.dart:44`~`:48`은 태그 입력을 사용하지 않아도 화면 진입 즉시 전체 태그 API를 호출한다. `tagSuggestionsProvider`가 `autoDispose`이고 상세 화면마다 `TagSection`이 새로 생성되므로 책을 차례로 열 때 같은 전체 목록 요청이 반복된다. 예외 처리 목적이라면 최초 포커스 시 생성한 Future에 즉시 오류 핸들러를 연결해도 달성할 수 있어, 선조회 자체는 필요하지 않다.
- [문제][중간][접근성/입력] `lib/features/book_record/screens/widgets/progress_card.dart:102`~`:120`은 쪽수 `TextField`에 `isDense: true`, 14px 글자, 상하 4px 패딩을 함께 적용한다. dense 입력은 48dp 최소 높이를 자동 보장하지 않으므로 실제 포커스 가능한 세로 영역이 텍스트 높이와 패딩 정도로 축소된다. 카드의 바깥 패딩은 `TextField`의 hit test 영역에 포함되지 않아 손가락으로 입력창을 선택하기 어려워진다.

## 개선 제안

- 고정 지연 후 가변 높이 섹션 전체를 스크롤함 → 추천 데이터가 실제로 표시된 다음 입력창과 제한된 추천 영역이 함께 보이도록 스크롤하고, `ensureVisible` 대상은 섹션 전체가 아니라 입력창 또는 추천 컨테이너로 좁힌다.
- 전체 태그를 한 번에 `Wrap`으로 렌더링함 → 빈 검색어에서는 상위 일부만 노출하고 검색 결과에도 표시 개수 상한을 두거나, 최대 높이를 가진 별도 스크롤 목록으로 구성한다.
- 화면 진입마다 전체 태그를 선조회함 → 최초 포커스에서 Future를 생성하면서 `.onError`를 즉시 연결하고 그 Future를 재사용해, 태그 기능을 사용하지 않은 방문에서는 요청하지 않는다.
- 쪽수 입력의 hit 영역이 시각적 높이와 함께 축소됨 → 글자와 내부 패딩은 현재 밀도를 유지하되 `SizedBox`/constraints로 최소 48dp 높이의 포커스·터치 영역을 확보한다.
