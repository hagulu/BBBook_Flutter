# 리뷰 결과

## 요약
- 새 PHOTO multipart 요청은 API 문서와 일치하고 `flutter analyze`도 통과하지만, 재시도 시 중복 생성과 영구 실패 파일의 반복 전송을 막는 처리가 필요하다.

## 문제점
- [높음][데이터 정합성] `lib/features/book_memo/data/book_memo_repository.dart:517-542`는 PHOTO 생성 POST가 성공한 뒤에야 응답의 `memoId`/`itemId`를 로컬 DB에 기록한다. 서버가 요청을 처리한 직후 응답이 유실되거나 앱이 종료되면 로컬 조각은 `server_id = NULL`, `is_dirty = 1`로 남고 다음 동기화에서 같은 `postPhotoItem()`을 다시 호출한다. 현재 API 요청에는 로컬 작업을 식별하는 멱등성 키가 없으므로 기존 메모에는 사진 조각이 중복되고, 제목 없는 신규 메모에서는 메모와 사진 조각이 함께 중복 생성될 수 있다.
- [중간][파일 검증·오류 복구] PHOTO API 문서는 `jpg/jpeg/png/webp`, 최대 5MB만 허용하지만 `lib/features/book_memo/data/book_memo_repository.dart:671-687`은 선택 파일을 확장자와 크기 확인 없이 그대로 보관하고 `lib/features/book_memo/data/book_memo_api.dart:110-121`은 그대로 업로드한다. 허용되지 않는 형식이나 5MB 초과 파일은 로컬 저장 성공으로 사용자에게 보인 뒤 백그라운드 push에서 항상 400으로 실패하고, dirty 상태가 유지되어 이후 동기화 때마다 동일한 영구 실패 요청을 반복한다.

## 개선 제안
- PHOTO 생성의 응답 유실 → 로컬 조각마다 영속적인 요청 ID를 저장하고 생성 API에 멱등성 키로 전달해 재시도 시 기존 생성 결과를 반환하도록 계약을 보완한다. 서버 계약 변경이 어렵다면 생성 결과를 재조회해 동일 로컬 작업과 매칭할 수 있는 식별자를 API에 추가해야 한다.
- 지원하지 않는 사진의 영구 재시도 → 로컬 DB에 조각을 확정하기 전에 확장자와 실제 크기를 검증하고, 필요하면 지원 형식·5MB 이하로 변환한다. 서버의 400 파일 오류도 재시도 가능한 네트워크 오류와 구분해 dirty 무한 재시도를 중단하고 사용자에게 수정 동선을 제공한다.
