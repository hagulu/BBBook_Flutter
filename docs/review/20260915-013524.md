# 리뷰 결과

## 요약
- 네이버 로그인 연동의 기능 경로(취소 판별, 토큰 획득, iOS 콜백, 로그아웃)는 정상으로 확인됐고, 남은 문제는 `main()`의 플랫폼 채널 실패 방어 부재, Android 보안 하드닝 해제, Apple 버튼 텍스트 배율 미대응, 그리고 확인이 필요한 네이버 Client Secret 노출 범위입니다. `flutter analyze`는 통과했습니다.

## 이전 리뷰 항목 종결

`20260914-172331` 리뷰 5건 중 3건 해소, 1건 부분 해소, 1건 미해결입니다.

- [P1 해소] 앱 재시작 후 네이버 SDK 로그아웃 미실행 — `_naverUsed` 플래그와 조기 반환이 제거되어 `signOutNaver()`가 `try/catch`로 감싼 무조건 호출이 됐습니다(`lib/features/auth/data/social_auth_service.dart:138`). `auth_repository.signOut()`도 이를 무조건 호출합니다(`lib/features/auth/data/auth_repository.dart:131`).
- [P2 해소] 로깅 방식 불일치 — `debugPrint`가 `developer.log`로, 작업명이 `[소셜 로그인]` / `[소셜 로그아웃]`으로 통일됐고 `provider=naver`를 key=value로 넘깁니다. 지적됐던 로그 중복도 실제로는 발생하지 않습니다. `auth_notifier._login`은 `on ApiException` 절에서만 FAIL 로그를 남기고(`lib/features/auth/providers/auth_notifier.dart:217`), 네이버 SDK 단계의 `SocialAuthException`은 그 절을 타지 않고 그대로 전파되므로 두 계층에서 중복되지 않습니다.
- [P2 해소] Apple 버튼 로딩 표시 누락 — `_loading == _LoadingProvider.apple`일 때 `Positioned.fill`로 스피너를 겹쳐 나머지 버튼과 피드백이 대칭이 됐습니다(`lib/features/auth/screens/onboarding_screen.dart:217`).
- [P3 부분 해소] 텍스트 배율 확대 시 라벨 오버플로우 — 아래 「Apple 버튼만 텍스트 배율에 대응하지 못함」 항목 참고. `SocialLoginButton` 3종은 해소, Apple 버튼만 구조적으로 미해소입니다.
- [P3 미해결] 카카오·네이버 심볼이 공식 배포 에셋이 아님 — `assets/icon/social/kakao.svg`, `assets/icon/social/naver.svg`는 여전히 단일 `path`로 직접 그린 도형입니다. 코드 주석은 각 사의 로그인 디자인 가이드를 근거로 색상·여백·radius를 맞춰 놓았는데 심볼만 자체 제작이라 근거가 어긋납니다.

### 이번에 확인한 정상 동작

지적 사항이 아니라, 검증했고 문제가 없어 종결한 항목입니다.

- 로그인 취소 판별은 양 플랫폼 모두 맞습니다. Android는 취소 시 `sendResult(NaverLoginStatus.LOGGED_OUT, ...)`로 응답하고(`FlutterNaverLoginPlugin.kt:296`) 앱의 `result.status == NaverLoginStatus.loggedOut` 분기가, iOS는 `sendError(message: "Login cancelled by user")`(`FlutterNaverLoginPlugin.swift:249`)로 응답하고 앱의 `errorMessage.contains('cancel')` 분기가 각각 받습니다.
- iOS 리다이렉트 콜백 경로가 실제로 연결돼 있습니다. `ios/Runner/Info.plist:72`의 `UISceneDelegateClassName`이 `$(PRODUCT_MODULE_NAME).SceneDelegate`를 가리키고, `ios/Runner/SceneDelegate.swift`가 `FlutterSceneDelegate`를 상속하므로 플러그인의 `addSceneDelegate` 등록이 동작합니다.
- iOS Profile 빌드도 네이버 키를 받습니다. Runner 타겟의 Profile 구성이 `Release.xcconfig`를 baseConfiguration으로 참조하며(`ios/Runner.xcodeproj/project.pbxproj:374`), 해당 파일이 `NaverKeys.xcconfig`를 include하므로 README의 "Debug/Release/Profile 모두 이 설정을 사용합니다" 기술은 정확합니다.

## 문제점

- [P2] `main()`이 플랫폼 채널 실패에 무방비라 앱이 아예 뜨지 않을 수 있음 — `lib/main.dart:21`: `await KakaoConfig.loadNativeAppKey()`가 `try/catch` 없이 호출되고, 그 내부의 `invokeMethod`(`lib/core/config/kakao_config.dart:15`)도 방어가 없습니다. Android 핸들러는 `packageManager.getApplicationInfo(...)`를 `when` 분기 밖 첫 줄에서 호출하는데(`android/app/src/main/kotlin/com/hagulu/nook/bbbook/MainActivity.kt:30`) 이 역시 `try/catch`가 없어, 네이티브에서 예외가 나면 `PlatformException`이 그대로 Dart로 올라와 `runApp()` 전에 `main()`이 중단됩니다. 결과는 아무 안내 없는 검은 화면입니다. 이전 구현의 `String.fromEnvironment`는 컴파일 상수라 실패 자체가 불가능했으므로 이번 변경으로 새로 생긴 실패 경로이고, 같은 채널을 쓰는 `signInWithNaver()`는 채널 호출을 `try/catch`로 감싸고 있어(`social_auth_service.dart:94`) 방어 수준이 비대칭입니다. 카카오 키 하나를 읽지 못한 것으로 앱 전체가 기동하지 못하는 건 실패 반경이 과합니다.

- [P2] `android:taskAffinity=""` 제거로 Flutter 기본 보안 하드닝이 해제됨 — `android/app/src/main/AndroidManifest.xml:13`: 이 값은 프로젝트가 임의로 넣은 것이 아니라 Flutter 앱 템플릿이 지금(3.44.8)도 유지하는 설정입니다(`packages/flutter_tools/templates/app/android.tmpl/app/src/main/AndroidManifest.xml.tmpl:10`). 빈 taskAffinity는 다른 앱이 동일한 affinity를 선언해 앱의 task에 끼어드는 task hijacking을 막는 하드닝이며, 기본값으로 되돌리면 affinity가 패키지명이 되어 이 보호가 사라집니다. 제거 사유(네이버 Custom Tab 인증 반환)는 주석에 적혀 있으나 실기기 검증 근거가 없고, 더 좁은 대안이 검토되지 않았습니다. 또한 `MainActivity`는 외부 공유 진입점(ACTION_SEND/VIEW, 커밋 39023c8)을 함께 갖고 있어 task 배치 규칙 변경이 외부 기록 가져오기 흐름의 화면 전환에도 영향을 줍니다.

- [P3] Apple 버튼만 텍스트 배율에 대응하지 못함 — `lib/features/auth/screens/onboarding_screen.dart:204`: `SizedBox(height: 48)` 안에 `SignInWithAppleButton(height: 48)`을 넣었는데, 이 위젯은 `fontSize = height * 0.43`(≈20.6)을 고정 높이 `Container` 안에 그립니다(`sign_in_with_apple-8.1.0/lib/src/widgets/sign_in_with_apple_button.dart:96,150-153`). `Text`는 여전히 사용자 배율을 반영하므로, 높이는 그대로인 채 글자만 커져 잘립니다. 반면 `SocialLoginButton`은 이번 변경에서 고정 `height: 52`가 `minimumSize: Size.fromHeight(48)` + 세로 패딩으로 바뀌어 배율에 따라 높이가 늘어나고 `maxLines: 1` / `ellipsis`도 지정됐습니다(`lib/features/auth/widgets/social_login_button.dart:67-68,82-83`). 즉 OS 텍스트 크기를 키우면 3개 버튼은 커지고 Apple 버튼만 48에 머물러 높이가 어긋나고 라벨이 잘립니다.

- [P3] 네이버 Client Secret이 앱 바이너리에 평문으로 포함됨 — `android/app/src/main/AndroidManifest.xml:82`(`com.naver.sdk.clientSecret`), `ios/Runner/Info.plist:49`(`NidClientSecret`): 두 값 모두 APK/IPA에서 추출 가능합니다. 네이버 Android/iOS SDK가 클라이언트 측 Secret을 요구하므로 연동 방식 자체는 불가피하고 이 구현의 결함은 아닙니다. 다만 README는 "웹과 동일한 Naver Application의 Client ID/Secret을 사용해야 기존 계정이 연결됩니다"라고 요구하는데, 이는 웹에서 쓰던 자격 증명이 이제 공개값이 된다는 뜻입니다. 기존 계정 연결에 동일 **Client ID**만 필요한지 **Client Secret**까지 필요한지에 따라 필요 없는 노출일 수 있습니다.

## 개선 제안

- `main()` 기동 실패 → `KakaoConfig.loadNativeAppKey()`의 `invokeMethod`를 `try/catch`로 감싸 실패 시 `isConfigured = false`와 함께 `''`를 반환하게 합니다. 이렇게 해도 `assertConfiguredForRelease()`의 release 가드는 그대로 동작하고(키를 못 읽으면 미설정으로 판정), debug/네이티브 이상 상황에서는 카카오 로그인만 막히고 앱은 정상 기동합니다. Android 핸들러의 `getApplicationInfo(...)` 호출도 `when` 분기 안으로 옮기거나 `try/catch`로 감싸, 모르는 메서드 호출 한 번에 메타데이터 조회가 따라 도는 구조를 없앱니다.
- taskAffinity 하드닝 해제 → 플러그인이 선언하는 `NidOAuthCustomTabActivity`는 affinity 지정이 없어 기본값(패키지명)을 쓰므로, `MainActivity`의 하드닝을 버리는 대신 매니페스트 병합으로 **그 Activity의 affinity를 맞추는** 쪽이 변경 범위가 좁습니다. 이 방식이 실기기에서 통하는지 먼저 확인하고, 그래도 안 되면 현재처럼 기본 affinity를 쓰되 주석에 "Flutter 템플릿의 task hijacking 하드닝을 의도적으로 포기했다"는 사실과 검증 결과를 남깁니다.
- Apple 버튼 배율 → 높이만 `MediaQuery.textScalerOf(context).scale(48)`로 키우면 **이중 확대**가 됩니다. 패키지가 그 높이로 `fontSize = height * 0.43`를 계산한 뒤 평범한 `Text`에 넘기고, 그 위에 다시 주변 배율이 곱해지기 때문입니다(이 파일에는 `TextScaler`/`MediaQuery` 처리가 전혀 없습니다). 배율 2.0에서 `fontSize`가 41이 되고 실제로는 약 82px로 그려져, 세로로 잘리는 대신 가로로 넘칩니다. 확대를 한 번만 적용하려면 바깥 `SizedBox`와 `SignInWithAppleButton`에 같은 `scale(48)` 높이를 넘기면서, 그 subtree를 `MediaQuery.withNoTextScaling(child: ...)`으로 감싸 패키지가 계산한 `fontSize`가 그대로 쓰이게 해야 합니다. 적용 후 배율을 올려 가며 높이·글자가 한 번만 비례해 커지는지 확인이 필요합니다. 로딩 오버레이의 `borderRadius`도 같은 값을 공유하도록 상수로 뽑습니다.
- 네이버 Client Secret 노출 → 백엔드 소스를 직접 열지 않고, **기존 웹 계정 연결에 동일 Client ID만으로 충분한지** 확인이 필요합니다. Client ID만으로 된다면 모바일 전용 Naver 애플리케이션을 별도로 만들어 웹 Secret 노출을 피할 수 있습니다. 동일 Secret이 필수라면 백엔드가 이 값을 기밀로 전제하는 검증 로직을 갖고 있지 않은지 함께 확인해 주세요.
- 브랜드 심볼(이전 리뷰 이월) → 카카오/네이버 개발자센터가 배포하는 공식 로그인 버튼 심볼로 교체하고, 교체가 어려우면 가이드 준수를 단정하는 주석 표현을 조정합니다.

---

정적 분석만 수행했습니다. 프로젝트 지침에 따라 앱 실행과 테스트는 하지 않아 네이티브 네이버 로그인 왕복(네이버 앱 설치/미설치, 취소, 로그아웃 후 재로그인, 다른 계정 확인창)은 검증되지 않았습니다. `flutter analyze`는 "No issues found"로 통과했으나 이는 컴파일 가능성만 증명하며, 위 문제점 중 어느 것도 이 검증으로는 드러나지 않습니다. 특히 taskAffinity 변경 효과와 텍스트 배율 확대 시 레이아웃은 실기기 확인이 필요합니다.


## 후속 반영

- 카카오 설정 조회: `PlatformException`/`MissingPluginException`을 처리하고 미설정 상태로 복귀합니다. 빈 키로 SDK를 초기화하지 않으며, 릴리스 필수 키 가드는 유지합니다. 따라서 릴리스 미설정 빌드를 차단하는 정책은 바뀌지 않습니다.
- Android 설정 채널: 지원하는 메서드만 메타데이터를 조회하고, 조회 예외는 민감 정보 없이 채널 오류로 반환합니다.
- Apple 버튼: 버튼 높이에 텍스트 배율을 적용하고 내부 배율을 비활성화해 이중 확대를 막았습니다. 버튼과 로딩 오버레이의 모서리 값을 공유합니다. 화면 배율의 실기기 확인은 미수행입니다.
- taskAffinity 변경 제안은 미반영합니다. 이 리뷰 이전 작업의 기기 로그에서 원래 작업 1771과 별도 반환 작업 1772를 확인했으며, 기본 affinity 복원 후 사용자가 로그인 성공을 확인했습니다. 리뷰의 실기기 근거 부재 판단은 이 기록을 반영하지 못했습니다. SDK Activity의 affinity까지 비우는 대안은 아직 검증하지 않았으므로 정상 동작하는 설정을 유지하고 README에 근거와 보호 설정의 차이를 남겼습니다.
- 네이버 자격 증명은 SDK 요구사항대로 유지합니다. Secret과 계정 식별을 구분하고 바이너리 추출 가능성을 README에 명시했습니다. 동일 Client ID를 유지하면서 다른 Naver 애플리케이션을 만든다는 제안은 성립한다고 확인되지 않았으므로 적용하지 않았습니다.
- 브랜드 심볼은 공식 에셋으로 확인되지 않았음을 README에 명시했습니다. 현재 코드의 가이드 주석은 Google 여백만 설명하며, 카카오·네이버 심볼의 공식성을 단정하지 않습니다.
