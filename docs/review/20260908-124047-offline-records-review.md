# 리뷰 결과

## 요약
- 로컬 계정으로 먼저 진입하고 인증·기록 전송을 뒤로 미루는 구조는 `docs/policies/offline-records.md`와 일치하고 `flutter analyze`도 통과하지만(테스트 기대값도 새 계약으로 갱신됨), 사용자 진입 경로가 백그라운드 전체 동기화에 묶이는 대기와 영구 실패 dirty 행의 무한 재시도가 남아 있습니다.

## 문제점

- [문제] [높음] 화면 진입이 백그라운드 전체 동기화 완료까지 대기한다. `background_record_sync_provider.dart:24`가 `ApiClient.prepareRecordSync`에 `beforeNetworkRequest`를 연결하고, `api_client.dart`의 `_onRequest`가 `requiresRecordSync` 요청마다 이를 `await`한다. `beforeNetworkRequest`는 진행 중인 `_inFlight`(인증 → 책 → 노트 → 독후감 → 태그 4단계 전체)를 통째로 기다린다. `/api/me/books/exists`(`book_detail_api.dart:43`)는 책 상세 로딩 경로(`book_detail_providers.dart:47`)에 있어 그동안 상세 화면이 로딩 상태에 머물고, `/api/me/privacy-setting`(`bookshelf_api.dart:62`, `:83`)도 프로필 진입·완독 공개 토글에서 같다. 이 대기는 요청 전송 *이전*이라 Dio의 connect/receive timeout이 적용되지 않으므로, 미전송 변경이 많으면 요청당 10초 타임아웃이 누적된 만큼 그대로 길어진다.
- [문제] [높음] 서버가 영구 거부하는 dirty 행이 하나라도 남으면 30초 주기 전체 동기화가 끝없이 반복된다. `BackgroundRecordSync._run()`의 "최근 10분 성공이면 생략" 조건은 `_hasPendingChanges()`가 true면 무력화되고, `bookshelf_repository._pushDirtyItem`은 `reportPermanentCreateFailure: false`(현재 `_pushCreatedBook`이 넘기는 값)일 때 400/404/409를 로그만 남기고 dirty를 유지한다. 예를 들어 다른 기기에서 이미 추가한 ISBN을 오프라인에서 추가하면 CREATE가 계속 409로 거부되고, `_upsertItemTxn`은 `client_request_id`가 다른 서버 사본을 별도 행으로 저장하므로 같은 책이 두 번 보이는 상태에서 앱이 포그라운드인 내내 4단계 동기화가 반복된다. 사용자에게는 실패 표시도 재시도 수단도 없다.
- [문제] [보통] 네트워크 백오프에 사용자 조작 예외가 없다. `api_client.dart`의 `_onError`가 연결 실패·타임아웃·5xx마다 `_retryAfter`를 15초로 잡고, `_onRequest`가 그동안 모든 요청을 전송 전에 거부한다. 백오프 자체는 정책(`offline-records.md` "네트워크와 갱신 실패 후 15초 동안 반복 요청을 제한한다")이지만, 최초 다운로드 화면의 "다시 시도", 프로필의 "다시 시도", 당겨서 새로고침처럼 사용자가 직접 누른 재시도까지 같은 창에 걸려 실제 요청 없이 즉시 같은 메시지를 돌려준다. 연결이 이미 복구됐어도 사용자가 앞당길 방법이 없다.
- [문제] [보통] 표지 파일이 사라지면 그 책의 미전송 편집이 영구 스톨한다. `bookshelf_repository._pushBookInfo`는 표지 사본을 `resolve`하지 못하거나 파일이 없으면 `ApiException('저장한 표지 파일을 찾을 수 없습니다.')`를 던진다. 이 예외는 `statusCode`가 null이라 `_pushDirtyItem`의 마지막 `else`로 떨어져 `reason=network` 로그만 남기고 dirty를 유지하므로, 같은 행에 묶인 기록 필드 편집(상태·진행률·평점)까지 영원히 서버에 도달하지 못한다. 위 무한 재시도의 연료가 되기도 한다.

## 개선 제안

- 진입 경로 대기 → `requiresRecordSync`를 "전체 동기화 완료까지 대기"가 아니라 "해당 책의 미전송 push만 선행"으로 좁히거나, `beforeNetworkRequest`에 상한(3~5초)을 두고 초과하면 그대로 요청을 보낸다. 함께, 동기화 경로에 `requiresRecordSync` 요청이 하나라도 추가되면 `_inFlight`가 자기 자신을 기다리는 교착이 되므로(현재는 해당 요청이 없어 발생하지 않는다), `_run()` 실행 중에는 `beforeNetworkRequest`가 즉시 반환하도록 가드를 둔다.
- 영구 거부 dirty → 행별 실패 횟수·마지막 사유를 저장해 400/404/409 같은 영구 오류는 재시도 간격을 늘리고, `_hasPendingChanges()`가 그런 행을 재시도 대상에서 제외하게 한다. 화면에는 "동기화 실패" 표시와 수동 재시도를 제공하고, 중복 ISBN 409는 서버 사본과 로컬 행을 합칠지 사용자에게 묻는 경로를 만든다.
- 백오프 → 사용자가 직접 실행한 재시도에만 백오프를 무시하는 옵션(`Options(extra: {...})`)을 두거나, 남은 대기 시간을 메시지에 포함해 지금 왜 막혔는지 알 수 있게 한다.
- 표지 유실 → 파일이 없으면 `bookCoverDirtyField`만 내리고(표지는 서버 값 유지) 나머지 책 정보·기록 변경은 계속 전송하도록 복구 경로를 만든다. 로그 사유도 `network`가 아닌 별도 사유로 남긴다.
- `_pushBookInfo`의 400 재시도 → 지금은 기록 PATCH의 400을 모두 "새 총쪽수 상한" 문제로 보고 book-info 반영 뒤 같은 요청을 한 번 더 보낸다. 영구 검증 오류면 매 동기화마다 400 요청이 두 번씩 나가므로, 재시도 조건을 쪽수 관련 오류로 좁히는 편이 안전하다.

## 후속 반영

- 선행 동기화 대기: 공통 API 준비 단계의 대기를 최대 3초로 제한했다. 이미 실행 중인 동기화는 기다리지 않아 재진입/순환 대기도 피한다. 시간 초과 후 동기화 자체는 계속 진행한다.
- 영구 오류: 책 행별 실패 사유·횟수·재시도 시각을 보존하고 10분~6시간으로 간격을 늘렸다. 보류된 부모와 하위 기록은 주기 동기화의 즉시 재전송 판단에서 제외한다. 새 편집/삭제·수동 책장 새로고침은 대기를 풀며, 수동 재시도 후 실패가 남으면 기존 스낵바로 알린다.
- 수동 재시도: 공통 `requestUserRetry`가 네트워크 및 인증 복구의 일시 오류 대기를 해제한다. 최초 다운로드/프로필 재시도와 책장/노트/독후감 새로고침에만 연결했다. 인증 무효 및 계정 검증은 우회하지 않는다.
- 표지 유실: 나머지 필드 전송을 계속하고 표지 교체만 dirty로 남긴다. 교체 의도를 자동 폐기하라는 제안은 채택하지 않았다. `local_cover_missing`을 저장하며 새 표지 선택 시 다시 시도한다. 이미 기록 PATCH가 먼저 성공할 수 있으므로 리뷰의 "모든 기록이 항상 전송되지 않는다"는 설명보다, 정보 저장 실패와 dirty 반복이 정확한 영향이다.
- 400 재시도: 진행률 변경이 있고 새 쪽수 범위에 맞는 경우로 제한했다. API 문서에 구조화된 쪽수 오류 코드가 없어 서버 메시지 문자열로 오류를 추측하지 않는다.
- 미반영: 중복 ISBN 자동 병합/병합 확인 UI는 노트·독후감·기록 충돌 정책이 필요하므로 추가하지 않았다. 원본 두 사본을 보존하며 자동 삭제·병합하지 않는다. 조용한 백그라운드 처리 요구에 따라 자동 실패 팝업도 추가하지 않았다.
- 검증: `flutter analyze`와 `git diff --check` 통과. 선행 대기 상한·명시적 네트워크 재시도·행별 재시도 지연/해제·늦은 실패 응답·표지 부분 확정에 대한 테스트 코드를 보완했다. 프로젝트 지침에 따라 테스트 및 앱은 실행하지 않았다.
